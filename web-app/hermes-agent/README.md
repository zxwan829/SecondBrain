# Hermes D078 guard overlay

This is a small user plugin for the fixed Hermes v0.22.2 source contract (`d923a5eb487a17c0a68801bba9ef0f56c81040a8`). It does not modify Hermes core files. Install the `d078-guard/` package as `$HERMES_HOME/plugins/secondbrain-d078-guard/`, enable it in the active profile, and merge `config.d078.yaml` while preserving unrelated profile settings.

The hook routes every `terminal`, `process_manage`, and `execute_code` call through Hermes' `pre_tool_call` `approve` gate with a fresh rule key. The Core browser bridge only submits `once` or `deny`; it never offers session or always grants. If approval is off, YOLO is active, another `pre_tool_call` hook could rewrite the execution arguments, the backend is not local, the workdir is missing/non-canonical, or arguments are outside the pinned tool contract, execution is blocked. Shell composition, dynamic expansion, multiline commands, common interpreter/wrapper entry points, and known script arguments are rejected. This does not inspect arbitrary executable behavior: an approved executable can start other programs or access files, and the approval is not an OS sandbox.

Generic Hermes file mutations (`write_file` and single-target replace-mode `patch`) are held at the same native Run approval gate. The guard resolves path arguments (including symlinks), places those canonical targets in the approval payload, and dispatches the same normalized arguments only after a user selects **Approve once**; the Core bridge binds the exact arguments digest to the authenticated owner, Session, Run and approval request. Missing, malformed, expired, disconnected, rejected, replayed or altered approvals do not execute. The approval card displays the target and complete arguments. Multi-file V4A `patch` payloads are blocked because their actual targets are embedded in patch text and cannot be represented by one verified target. Hermes internal state/credential paths and Skills remain hard-blocked for generic writes. The existing Core Capture API remains a separate, unchanged write path.

The same hook blocks file reads/searches of Hermes sessions, state, config, credentials, pending queues, and internal memory, including ancestor search roots, normalized paths, and symlink targets. It also blocks common credential stores (`.ssh`, `.aws`, `.gnupg`, `.docker`, `.kube`) and secret-file names/extensions. Generic writes into Skills remain hard-blocked so `skill_manage` remains subject to `skills.write_approval`. Ordinary business-file reads are not placed behind a global allowlist. Existing Knowledge read-only mounts and Capture safe-write roots remain required runtime controls; user approval does not alter filesystem mounts or OS permissions.

The profile template deliberately leaves the API terminal toolset disabled. Do not add `terminal` to `platform_toolsets.api_server` until the deployed fixed image has loaded this plugin, has no other execution-rewriting pre-tool hook, and has passed an approval-request-to-Core-UI-to-Run-approval exercise. Do not launch Hermes with `--yolo`; the hook blocks execution if YOLO or approvals-off is detected, but the profile must remain `manual` as defense in depth. Do not remove other active profile settings when merging the fragment.

Skill changes are reviewed in the Hermes CLI with `/skills pending`, `/skills diff <id>`, `/skills approve <id>`, and `/skills reject <id>`. The Web App has no Skills approval page in this stage. The generic `file` tool cannot write into `$HERMES_HOME/skills/`; `skill_manage` is the only agent-side write path and stages changes when `skills.write_approval: true`.

Core stores Run and approval ownership in process memory. This requires the current single-process Core deployment model. A Core restart invalidates approvals; a Hermes/Core disconnect or missing browser consumer leaves the native Run approval unanswered, which Hermes rejects on timeout. Approval is not an OS sandbox: a user-approved command runs with the Hermes worker's OS permissions. Private must remain unmounted and Knowledge read-only. The terminal approval card shows the exact tool arguments, but it cannot preview arbitrary effects of a permitted executable or mutable files it reads; indirect scripts and shell composition are therefore blocked by the hook.

Rollback is to keep API terminal excluded and remove the enabled plugin/config fragment; the D077 JSONL store and Core learning code are unchanged. Production plugin installation, profile merge, image/config changes, service restart, and post-deploy verification require separate authorization and review.
