# 业务规范

> **业务域：SecondBrain 笔记（Notes）**。本文件是后续笔记业务需求、规则与产品决策的统一维护入口；新增或修改笔记业务规则应更新本文件，不在多个临时 D085 规格中重复维护。技术实施、当前交付状态和测试证据分别参见 Architecture、00-CURRENT 与关联 Issue/PR。

> **适用范围**：SecondBrain/Obsidian Vault 的笔记组织、对话收录及标签与类型产品规则，为 D085-C2 与关联功能设计输入。**产品方向已确认，不代表代码已实现、生产已授权或现有目录权限已改变。** 与 `Architecture.md`、`Agent-Rules.md`、现有正式 Knowledge/Review/Promote 边界共同适用。关联 Issue #46、#55；重大取舍见 `Decision-Log.md` D086。

## 1. Vault 目录树：已确认顶层与拟议回收站

用户提供的 Obsidian 文件管理器截图确认的**完整可见顶层**如下（截图没有展开子文件夹，不能推断内部子目录）：

```text
SecondBrain / Obsidian Vault/
├── 00-Inbox/
├── 10-Review/
├── 20-Knowledge/
├── 30-Projects/
├── 40-Memory/
├── 50-Journal/
├── 90-Archive/
└── Home.md
```

**拟议新增功能，不表示已创建磁盘目录**：

```text
SecondBrain / Obsidian Vault/
└── [回收站 Trash：逻辑功能／物理存放位置待确认]
```

- `00-Inbox`：统一笔记记录入口；Capture/Raw 的现有存储与权限边界仍有效，待 C2 核实内部结构后才能划分 Notes 可写区域。
- `10-Review`：现有审核流程；不是 Notes 可任意写入的目录。
- `20-Knowledge`：正式知识；现有 Human Approval/Promote 边界不变。Vault 全量浏览/编辑是产品方向，**不代表现在可将 Knowledge 根设为通用可写**。
- `30-Projects`：项目资料及笔记关联；关联项目优先记录引用/元数据，不强制移动原始文件。
- `40-Memory`：个人记忆业务区域；不借普通 Notes API 获得写入权限。
- `50-Journal`：现有日记业务区域；进入日记应走原有 Journal 语义/API 而非直接移动文件。
- `90-Archive`：**截图确认已存在，保留原样**。用户明确不新增产品“归档”工作流；不能据此删除或迁移既有文件。
- `Home.md`：Vault 根目录首页文件，保留。
- **Trash 回收站**：用户要求新增删除恢复能力、不要归档。优先调研 Obsidian 当前删除设置及与 `.trash` 的兼容性；是否放在 Vault 内、实际目录名、排除搜索规则与清理策略待 C2 决定。**不立即创建 Trash 目录**。删除前考虑笔记附件是否被共享引用；恢复时防止覆盖同名文件，并保存原路径；彻底删除需二次确认。原有 `90-Archive` 不等同 Trash。
- `.obsidian`（若存在）为 Obsidian 隐藏配置目录，截图不可见，不能声称当前实际结构已核实；通用 Notes 不得编辑其配置文件。

## 2. 笔记分类：文件夹 + Markdown 属性

**文件夹表示物理位置和现有业务边界，属性描述内容，标签标记主题。** 不强制给思考、会议、头脑风暴等内容新建独立分类文件夹。

### 2.1 全部新内容统一收件箱 → AI 分类建议 → 用户审批

**统一业务原则：凡用户明确收录，或经询问同意收录的新内容，无论是随手笔记、思考、会议纪要、头脑风暴、摘要、日记意图，还是通过 Capture 等入口接收的资料，都先由 Core 保存原文和来源到统一业务收件箱 `00-Inbox`；采集时不要求用户预先分类、选目录或决定最终归属。普通聊天本身仍是聊天，不逐句自动收录。** “同一业务入口”指统一的用户收件箱视图与处理流程，并**不要求突破现有 Raw/Capture 安全隔离、把所有不同数据格式写进一个无边界的物理目录**；物理落盘映射和既有 Capture 专用根要在 C2 设计时核对。

- 所有新内容先统一进入 Inbox，保留原始内容和来源信息；原生 Markdown 笔记在 Vault `00-Inbox` 的具体可写位置须先解决现有 Capture 权限隔离。不强制创建生产独立 `Drafts`。目前 D085-A 的 Drafts 是隔离测试/既有 API 起点，不能直接认定已被替换。
- AI 可在受控元数据中选用既有类型、标签并建立关联；可建议日记、知识 Review/Promote、项目关联及其他后续操作。**AI 不经用户批准不得把内容移出 Inbox、覆盖/删改原文或执行正式知识/日记写入**；元数据自动维护遵循第 4 节。
- 用户可逐项确认、调整或拒绝建议；未审批/未处理的内容继续留在 Inbox，不因 AI 已完成识别而视为已整理。审批成功后保留可追溯来源与执行结果。
- AI 后续分析并提出**可预览、可修改、可拒绝**的建议，用户审批后再执行对应业务操作；AI 不得擅自改写正文、物理移动文件、删除笔记或 Promote 正式知识。
- 整理结果可同时包含：提炼日记（既有 Journal 业务语义）、提交正式知识（Review/Promote/Human Approval）、关联项目（优先引用/元数据，不强制挪动 Markdown）。**不是三选一互斥分类**；原笔记在生成目标内容确认持久化前始终保留。
- `状态`等系统元数据可按规则自动维护，但状态自动化不能绕过对正文、正式知识、日记业务写入与文件移动的审批。

### 2.2 第一版属性约定

| 属性 | 默认值与取值 | 维护规则 |
|---|---|---|
| `类型` | 日记、笔记、头脑风暴、摘要、会议纪要 | 中文字段；五个初始建议值，受第 4 节集中类型库管理；不是可以无限扩张的自由枚举 |
| `状态` | 待整理、整理中、已整理 | AI/系统自动更新；新笔记默认待整理；实际开始已授权整理后为整理中；完成保存与必要审批后才标记已整理。用户无需常规维护 |
| `创建日期` | 日期时间 | 新笔记创建时设置、后续不覆盖；已有笔记先尊重现有元数据，缺失时**优先可证实的原始导入日期**；再按可靠文件时间回填，来源不明不能臆造 |
| `修改日期` | 日期时间 | 每次成功保存笔记后更新；已有笔记优先采用可证实的最后修改时间；不要由属性更新自身触发无限保存 |
| `tags` | 如 笔记、CRM、SecondBrain | Obsidian 特殊属性名保持英文 `tags`；标签值由第 4 节集中标签库管理，Hermes 可自动应用既有有效标签；标签不强制与 `类型` 同步 |

- 普通自定义属性名称和值允许中文；`类型` 与 `tags` 的可用词汇按第 3 节集中管理。五种默认类型不硬编码为不可修改的系统字段。
- Obsidian 内置特殊属性键（尤其 `tags`）保留兼容拼写；标签既可放 frontmatter 的 `tags` 属性，也可在正文出现 `#CRM`。
- `类型: 笔记` 和 `#笔记` 可以同时出现，二者含义不同；不自动从类型复制出同名标签。
- 日期展示暂按 `YYYY-MM-DD HH:mm:ss` 目标约定；具体 YAML 日期类型、时区、Obsidian 属性编辑器解释及同步行为在实施前做兼容性测试；不能假定任意文本格式都能自动被 Obsidian 视为日期型属性。
- 对历史笔记不执行自动批量属性回填，必须先支持预览、备份、来源说明和审批。导入日期不等于内容原始创作日期。

示例：

```yaml
---
类型: 会议纪要
状态: 待整理
创建日期: "2026-10-17 19:15:00"
修改日期: "2026-10-17 19:15:00"
tags:
  - 笔记
  - CRM
---

# CRM 运营策略讨论
```

## 3. 对话收录与 Hermes 主动协作（批准的目标行为）

- 日常 Web Chat 和未来微信机器人默认是自然聊天。Hermes 可在当前对话中判断一段信息值得保留时，以自然语言询问是否收录；应有较高触发门槛，避免每句话都问。用户从一开始就允许询问、追问拒绝原因，并通过纠正和使用历史逐步学习何时询问；此判断由 Hermes 提出，Core 控制来源、授权、持久化及审计。阈值数值和学习机制留给后续验证，不把提示词当安全门禁。
- 用户明确说“收录”或同意询问时，Core 应立即把原文、时间、渠道和来源保存到 Inbox，并明确返回成功或失败，不再要求第二次“是否收录”确认。日记碎片、碎碎念即使无需 AI 精简，也先保留原文到 Inbox；随后才可建议形成 Journal，用户确认后由 Core 专用 Journal API 写入。此入口顺序取代 D064/D077 中聊天日记意图直接追加 Journal 的产品规则；已有 Journal 记录不因新规则被迁移或改写。Task 的明确意图仍走其专用业务授权，不能借日记规则推断自动创建待办。
- Hermes 可回顾获准的历史聊天、SecondBrain/Obsidian Vault、Task、个人记忆等数据，结合当前对话主动提出收录、关联或整理建议；Private 仍排除，尚无其他外部私人数据源。可自主搜索公开互联网，但不得把私人内容写入搜索词；网页信息须标明来源，不能当成用户本人事实。向外部服务发送私人数据另需授权。
- Hermes 可在非聊天时主动回顾与联系用户，初期不设固定免打扰时间；用户反馈“太晚”等应形成可修正的软偏好。Web 设置需分别控制**主动回顾频次**与**主动联系频次**，并可关闭。主动建议必须说明依据，可忽略、纠正，建议不等于执行。
- Core 对主动任务和用户发起的被动聊天分别维护**每日与每月估算金额额度**，Web 设置可同组展示两池。金额按预计 Token、所选模型价格及可能的付费搜索成本估算，并显示预计消耗；允许小幅估算误差，不能冒充结算账单或供应商硬限额。主动额度不足即暂停后台工作；被动额度不足时，先提示本次预计金额，由用户选择临时追加额度或稍后再聊，追加须有明确金额和记录。Hermes 决定建议内容与合适时机，Core 在付费调用前执行预算门禁。

## 4. 标签与类型集中管理（独立功能，关联 Issue #55）

- 标签与类型在独立管理功能中统一维护，可位于同一设置类别。每条笔记最多一个主类型，可有多个标签；`状态`、`创建日期`、`修改日期`由系统按既定规则维护，不纳入词汇库。项目分类由用户手动添加，不强制纳入此功能。
- **类型库最多 10 种。** Hermes 可为未手动设置类型的笔记自动选用既有类型，用户可事后改正，无须逐条批准；不得自动覆盖用户为该笔记手动设置或修改的类型，只能建议。新增类型由 Hermes 提议、用户确认；达到 10 种时先建议合并或停用，不自动扩容。类型与标签是两套词汇，不互相复制。
- **标签库是规范词表。** Hermes 可给获准处理的 Inbox 笔记和历史内容自动应用现有有效标签，允许用户撤销或纠正；用户手动移除某笔记的标签后，不得给同一笔记自动加回同一标签。新标签、标签停用及持久同义词映射均需用户确认；明确同义词可直接选用已有规范标签，含糊时询问。停用只停止未来自动使用，保留历史引用；实际删除或批量替换须预览影响并另行批准。避免“AI 技术/人工智能”这类重复标签。
- 对正式 Knowledge，Hermes 可自动更新 **SecondBrain 受控的标签与关联元数据**，不能直接改写 Knowledge Markdown 正文/frontmatter。拟回写正式 Knowledge 的候选须展示精确目标与改动，由用户单独审阅确认，Core 核验身份、目标、版本和执行结果。候选可在 Chat/微信提示并在 Web 待办区展示，使用同一审批记录；微信身份无法可靠绑定时转 Web 确认。Raw、Review、Journal、Memory、Private 继续遵守各自边界；历史普通笔记的写权限仍按目录逐项审定，不因“全 Vault 浏览”获得递归写权。
- 初始标签/类型库先对获准的 Obsidian/SecondBrain 数据做**只读盘点**，列出现有值、近义或重复候选，由用户审阅；不得直接批量改写历史文件。真实 Vault 读取及后续迁移各需独立操作授权。

## 5. 与当前实现和安全约束的关系

- 当前 Notes/Tiptap 可能对含 YAML frontmatter 或 Obsidian 特有语法的 Markdown 采取只读保护。**自由编辑属性、日期自动更新及 Inbox 原生新建属于后续需求，不宣称 C1 已实现**。要设计安全的 frontmatter 属性编辑接口，未知键、字段顺序/注释及正文尽可能保留，无法安全转换时 fail-closed。
- 笔记正文的权威仍是 Vault 内 Markdown；可编辑脑图/画板以单独源文件及 Markdown 相对链接关联；不得新建割裂的第二套笔记 SoT。
- Notes 全 Vault 浏览和用户手动编辑是产品目标；正式 Knowledge、Raw、Review、Memory、Private 及系统目录的现行权限与审批机制在 C2 特别评审前不变。**不存在“整个 Vault 递归 RW”默认授权**。
- 删除采用安全回收站而非立即销毁；与 Obsidian 的删除和同步方式、共享附件以及源路径恢复冲突的行为待 C2 设计和测试。
- C2、主动回顾和标签与类型管理尚无因此新增的 NAS 部署、生产配置写入、真实文件读取/修改、付费模型或真实用户数据出站授权；本规范本身不授予任何上述权限。

## 附录：Daily Brief 形成与来源规则（D087，2026-10-20 已批准）

- V1 首先采用**用户人工触发，或用户明确批准后导入已有简报记录**。Core 应在核验来源引用、版本与权限后持久保存日期/时区、生成或导入时间、摘要、来源引用及状态；Web 只读取经 Core 判定可信的记录。未经核验的正文不得被当作可信日报展示。
- `GET /api/daily-brief` 严禁临时生成、抓取聊天或调用付费模型；未配置、部分来源、过期、失败应准确降级，不能用前端拼接冒充已生成简报。
- **每日定时自动生成以后独立决策**，本次没有批准生成 API 生产执行、写入业务数据、真实 Vault/简报读取、NAS 部署、后台任务、模型/费用或 Promote。具体实现和只读验收方案参见 `business-specs/Projects-Daily-Brief-Source-and-Read-Release-Plan.md`；正式取舍见 `Decision-Log.md` D087。
