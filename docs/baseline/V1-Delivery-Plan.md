### 1.2 当前真正的四类缺口

1. **代码与可用产品之间的缺口**：Planning 的模拟执行、Brief 的 501、Activity 有限来源、Home 占位和部分模块未接真实数据。
2. **智能效果缺口**：metadata-only 来源展示不等于模型读到合法上下文，更不等于自然召回、纠错和可信回答已通过。
3. **权限与生产缺口**：Linux Core-peer 子集已通过；独立批准来源、Authority-only、Writer 自身严格写限制、Raw/状态同 UID 风险和生产拓扑仍需处理。
4. **协作缺口**：旧 Issue/CURRENT 的状态落后于评论；多个历史 Draft 与已集成成果混在一起；单项门禁经常让另一线无事可做。

## 2. 完整 V1 范围与完成定义

范围以 Web App V1 Business Spec、Universal Capture v1.1、D077/D078/D086/D087/D088/D089、业务规范及既有 Notes 决定为依据。保留原 MUST、已批准 Companion MVP，以及本用户要求一并交付的 Notes/标签等扩展。**不以“基本闭环”、只读演示、全部 PR 已合并替代完整 V1。**

- 原 V1：Shell/导航/认证，Home，Chat，Today/Calendar，Inbox，Review/Approval，Projects，Knowledge，Daily Brief，Activity/Agent Health，模块扩展契约，多端，Private/受控写入，恢复和同步。
- 输入：文本/Markdown/TXT/Capture Context、URL、PDF、图片/截图、语音/音频、Web、微信；原件、来源、partial、重试与安全处理不可缺失。
- 智能：无检索指令的相关联想、跨会话低风险学习与纠错、准确事实回源、自然语言 Journal/Task、受控主动回顾/建议、重复反馈形成可审经验/Skills。
- 既有扩展：Markdown 可迁移编辑、图片附件、可编辑脑图/画板、统一 Inbox、标签/类型中心、受控元数据、删除恢复/同步冲突；已实现的部分只补缺口和验收。
- D086 成本：主动/被动两池、每日/月度估算金额、主动回顾/联系频次分开、关闭与用户纠正；被动超额先显示预计金额，用户明确追加或稍后再聊。
- D088 Brief：个人 Task/Project/Journal；用户触发生成或批准导入，不做新闻，不把主动 Companion 的后台回顾误接成 Brief 自动定时生成。

**飞书口径**：D087 已批准共用 Hermes/Core 的接入架构，但正式 UC MUST 明列 Web/微信，未同样写明飞书上线为 V1 MUST。本计划将飞书放入同一渠道交付包，保留实现与验收事项；PMO 在 P4-2 合同冻结时一次明确首版支持矩阵，不能凭本文暗中删掉用户已批准渠道，也不能将“架构方向”虚报成已上线。若完整 V1 对飞书上线承诺尚未明确，必须在 #76 保留一条范围待决，不能带着该待决宣布范围无遗漏。

**继续延期**：Office/视频/任意二进制、向量库/RAG/复杂知识图谱、第二 Agent Runtime、原生手机 App、公网商业发行、Books/People 等独立业务模块。原 SHOULD 不因本计划自动升为 MUST；D077/D086 已明确提升的自然语言能力、费用与主动控制按批准要求交付。

完整 DONE 需要：每项必交能力有源码/复审、必要测试、适用的真实运行证据及用户验收；安全和原件保护成立；恢复可操作；没有未披露的 P0/P1 或核心能力 BLOCKED。允许不妨碍业务闭环的已登记小修，不允许把必要能力缺失记为小修。

### 11.3 布局不稳定的处理方案

此前不稳定的具体根因尚未在本轮复现，不能直接归因于模型或缺少某插件。改版启动时选一条真实失败案例检查 DOM/CSS、共享样式、响应式与截图差异；优先核实父容器约束、全局样式串扰、绝对定位补丁、字体/长文本变化和视口不一致。

A 建立一份项目内的简短设计/布局规范，内容包括：

1. **设计变量**：统一间距、字号、行高、颜色、圆角、内容最大宽度、侧栏宽度和断点；共享组件优先引用变量。参数由已确认样板确定，不随每次口头调整随机变化。
2. **关系规则**：把“向右一点”转成目标容器、对齐对象、内边距、最小/最大宽度、换行与滚动规则；优先 Grid/Flex 表达关系。仅在真实覆盖层等适用场景使用绝对定位，不靠连续增加负margin/transform掩盖结构问题。
3. **修改边界**：一次修改写清目标组件、受影响断点和预期变化；确认共享样式会影响哪些页面。检查父容器和关联组件后再改，禁止无依据顺手全站改样式。
4. **可观察反馈**：运行真实页面，固定合成内容、字体加载、浏览器版本、视口、缩放和动画状态；交付修改前/后/差异截图及实际操作预览。用户只需看效果，不需读CSS。
5. **几何与交互断言**：主操作按钮可见可点，关键组件在预期容器内、对齐关系成立，无非预期横向滚动/遮挡；测试长标题、中文、空态/错误、窄屏和编辑器滚动。允许正常响应式变化，不将整个页面坐标写死。
6. **基线控制**：截图变化由已确认设计解释，不能直接更新golden或扩大容差来“修复”失败。只遮罩真实动态内容，不遮罩正在修改的组件；相关页面视觉与业务一起核验。
7. **角色隔离**：A统一负责前端布局/共享组件；B仅提供稳定接口/合成fixture及必要性能修复，不同时修改同一CSS或App布局。

Playwright 提供截图比较；其官方文档特别指出不同操作系统、版本、设置和运行方式会影响渲染，因此基线与复验需使用同一环境。小范围视觉变化只做相关页面/组件验证，不每次跑全站。[Playwright 视觉比较与环境要求](https://playwright.dev/docs/test-snapshots)

| U2 设计规则与样板 | 固定Shell/导航、组件变量与移动布局；建立UI skill和组件样例；将用户自然语言改动转成关系规则 | 核查既有接口兼容，不增加无关端点 | 样板桌面/平板/手机预览一次确认；用户无需自己操作设计工具 |
| U3 代表页面完整落地 | 完成样板页全部正常/空/错误/长文本状态及真实交互；截图/几何/定向业务验证 | 修复有证据的接口/状态缺口 | **UI_STABILITY_GATE**：同页连续3轮代表性位置调整，目标变化达成，未修改区域/其他断点无非预期回退；任一失败就在样板内修复 |
| U4 分批全站迁移 | 样板稳定后按Shell→Home/Chat/Today→Inbox/Review/Knowledge→Projects/Brief/Activity→Notes/设置分批迁移，复用组件 | 维持数据和权限合同；必要适配明确版本 | 每个完整页面组集中确认，不逐按钮停工；保留可回退发布点 |
| U5 多端与性能复验 | Desktop/iPad/iPhone、键盘/触控/IME、滚动/长文、可访问性及加载表现；复用V1关键旅程 | 按真实瓶颈定向修复，不因改版重写Core | 组合视觉+功能Gate；截图好看但核心动作失败不能通过 |
| U6 接受与发布 | 用户接受后的候选、回退说明、必要文档与授权部署 | 运行支持和定向缺陷修复 | 用户最终体验确认；生产发布仍走具体授权 |

三个小试调整建议：调整侧栏宽度且正文保持对齐；移动主要操作区但长标题不挤压按钮；改变桌面卡片排列且手机阅读顺序正确。以上是本项目拟定的验收方法，不是宣称已有测试结果。

**选型决定方式**：先让用户通过普通浏览器预览验证U1～U3。若本地预览+规范+截图闭环足够稳定，Figma保持可选；若设计反复或需要长期维护设计稿，再安装/连接并验证Figma能力。需要插件时由用户完成必要账号授权，A负责技术配置；不要求购买付费服务或邀请其他设计人员作为默认前提。外部工具仅使用合成/脱敏页面素材，真实私人内容不自动上传。

**最终承诺形式**：交付可观察、可回归的改版流程和稳定样板，再推广全站；不承诺“装一个美化skill就永不跑版”。本章已纳入本次规划，尚未实施UI、安装工具或运行视觉测试。
